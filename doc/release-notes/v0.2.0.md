Feature release: the three items 0.1.2 listed as unimplemented are gone, and
the first integration tests against real database servers found that the
MySQL/MariaDB module had never worked at all.

**[API reference](https://xcomart.github.io/libcmdbm/api/)** ·
**[Project page](https://xcomart.github.io/libcmdbm/)**

## Added

* **The configuration may be written in XML.** `CMDBM_ContextCreate` takes
  either form and decides by the content, not the file name: a file whose
  first non-blank character is `<` is parsed as XML. The tree is converted
  into exactly the object the JSON form produces and handed to the same
  parser, so there is one set of configuration semantics rather than two.
  The tag name of a datasource is its DBMS type, attributes and scalar child
  tags are both keys, `<Param>` fills the params object, and an unknown tag
  is skipped with a warning instead of rejected. `data/cmdbm_config.xml` is
  now the XML spelling of the JSON sample and validates against
  `data/cmdbm_config.dtd`, which had unterminated content models, an
  `ATTLIST` naming the wrong element and undeclared elements.
* **The `Logging` configuration section is implemented.** `queryId` and
  `query` choose what is logged before a statement runs, `result` adds the
  outcome afterwards — the affected row count, the result JSON, or one line
  per row for `ForEachRow`. Everything stays at DEBUG on the
  `cmdbm.session` logger. The defaults are `queryId` and `query` on,
  `result` off, which keeps the previous behaviour and leaves the
  potentially large one opt-in.
* **`monitorInterval` can be set from the configuration.** The DTD had
  documented it but neither form implemented it, so the mapper rescan
  interval could only be set from code. It is a datasource key in JSON and
  an attribute of `<Mappers>` in XML.
* **Integration tests for the client/server modules.**
  `test/docker/compose.yml` brings up a MariaDB 11 and a PostgreSQL 17, and
  `test/docker/env.sh` points the tests at them. A test whose variables are
  not set exits with 77, which ctest reports as a skip, so a checkout
  without docker still runs the suite green. Both tests build and drop their
  own schema and cover bind variables of every JSON type, `GetObject` /
  `GetRow` / `GetRowSet`, `resultType="value"`, the dynamic tags,
  transactions, cursor iteration with a `fetchSize`, `<selectKey>` and OUT
  parameters.

## Fixed

* **`#{…, mode=out}` had never worked, in any module.** The mapper split the
  parameter expression to look for the attribute and passed the
  `CMUTIL_String` object where a C string was expected, so what it compared
  against `"mode"` was the raw bytes of a structure. Every OUT parameter had
  been built as an ordinary bind variable since the syntax was introduced,
  and the OUT binding code of the Oracle and ODBC modules had never run.
  Nothing failed loudly — the statement executed and the value simply never
  came back.
* **OUT parameters on PostgreSQL.** PostgreSQL has no OUT binding, but it
  does not need one: `CALL procedure(...)` hands the OUT and INOUT values
  back as a single result row, whose columns are now written into the OUT
  parameters in declaration order.
* **OUT parameters on MySQL/MariaDB.** The server sends them as an extra
  result set flagged `SERVER_PS_OUT_PARAMS` rather than writing back into
  the bind buffers, which is what the module used to read. That set is now
  located and read. It is only visible to a statement run through `Execute`,
  so a `CALL` has to be written as an insert, update or delete; a select
  carrying OUT parameters says so in the log.
* **The MySQL/MariaDB module could not open a connection.** `Initialize`
  built the character set name with `Replace("-", "")`, which libcmutils
  returned NULL for, and `OpenConnection` dereferenced the result — every
  connection attempt was a segmentation fault.
* **Every string bind variable on MySQL/MariaDB failed.** They were typed
  `MYSQL_TYPE_VARCHAR`, a server-side type which
  `mysql_stmt_bind_param` rejects.
* **A successful `CALL` was reported as a failure on MySQL/MariaDB.**
  `Execute` returned `mysql_stmt_affected_rows` cast to `int`, and a `CALL`
  reports an unknown count as `~0`, which arrived as the `-1` this API uses
  to mean the statement failed.
* Two heap use-after-frees in the MySQL/MariaDB result binding, where the
  bind array was released before the field descriptions that point into it.
  Both were found by AddressSanitizer.
* A null bind value on PostgreSQL was cast to `varchar`, which made the
  server refuse it for every column that is not text.

## Changed

* libcmutils updated to **v0.6.5**. `CMUTIL_String` treated an empty append
  as an error, so `Replace(needle, "")` — the spelling for removing a
  substring — destroyed its result and returned NULL. That is what crashed
  the MySQL module. The same defect made `XmlSetName("")` log an error with
  a stack trace for every empty name, which put six to thirteen ERROR lines
  into each of our tests and buried real ones.
* The README documents the XML form, the `Logging` section and what an OUT
  parameter does per module.

## Known limitations

* **OUT parameters are unverified on Oracle and ODBC.** Both modules have
  carried OUT binding code for as long, but the mapper defect above kept
  `mode=out` from ever reaching a module, and there was no server to try it
  against once that was fixed. Treat it as untested rather than as working.
* **MySQL/MariaDB cannot read OUT parameters from a `<select>`** — see
  above.
* The Oracle prefetch remains verified by compilation only. The PostgreSQL
  streaming cursor and the MySQL server-side cursor are now exercised
  against real servers, as is everything else in the two modules.
